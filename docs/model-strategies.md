# Chat model strategies

The HTTP server is independent from the model pipeline. Select a pipeline with
`MODEL_STRATEGY`; no source edit is required.

## Available strategies

| Strategy | Profile generator | Candidate calls | Final answer |
| --- | --- | --- | --- |
| `baseline_l2` | — | 1 × L2 | L2 |
| `direct_l2` | — | 1 × L2 | L2 |
| `siusiubeom_h4` | GPT-5.6 Sol, with L2 fallback | L2 planner + L2 writer | L2 |
| `multi_patient_sol` | GPT-5.6 Sol | N × L2 | GPT-5.6 Sol |
| `multi_patient` | GPT-5.6 Sol | N × L2 | GPT-5.6 Sol |
| `patient-sim` | Lunit patient simulator + GPT-5.6 Sol prep | 1 × L2 diagnosis | GPT-5.6 Sol |

`siusiubeom_h4` with the `l2_plus` backend is the selected submission pipeline.
Its final answer is generated by L2. The evaluation environment has no general
external network access, so its planner falls back to L2 if GPT Sol is not
reachable.

`baseline_l2` is the canonical experiment name for the bare L2 harness. `direct_l2` remains as a
backward-compatible alias; both execute the same `DirectL2Strategy` implementation.

`patient-sim` sends the complete incoming history to Lunit's patient simulator for one added
patient question, asks Sol to turn the source conversation and that question into a fact-separated
clinical intake note, asks L2 for a diagnostic assessment, and asks Sol to write the user-facing
answer. `patient_sim` is an underscore alias. Any failed stage or pipeline timeout falls back to a
direct L2 answer over the untouched incoming history. A simulator 502 is retried; a 404 continuation
is retried once as a new conversation, as specified by Lunit's simulator contract.

`siusiubeom_h4` migrates the existing `app.engine` model into the registry without changing its
behavior: a Sol planner (or L2 planner fallback) creates a concrete brief, L2 writes the medical
answer, and the assembler enforces emergency/context behavior. `siusiubeom` is a short alias.

## Run locally

```bash
source .venv/bin/activate
pip install -r requirements.txt

export MODEL_STRATEGY=multi_patient_sol
export OPENAI_API_KEY="..."
export LUNIT_FM_API_KEY="lunit_..."
export PATIENT_PROFILE_COUNT=3

uvicorn app:app --host 127.0.0.1 --port 8000
```

Then send any OpenAI-compatible non-streaming chat request:

```bash
curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"multi_patient_sol","messages":[{"role":"user","content":"I have had a headache for two days. What should I do?"}]}'
```

The configured `MODEL_STRATEGY`, rather than the request's `model` field, selects the pipeline. This
prevents an evaluator-provided alias from unexpectedly changing the submitted implementation.

## Configuration

| Variable | Default |
| --- | --- |
| `MODEL_STRATEGY` | `siusiubeom_h4` in the submitted image |
| `L2_BACKEND` | `l2_plus` in the submitted image |
| `PATIENT_PROFILE_COUNT` | `3` |
| `MAX_PARALLEL_L2_CALLS` | profile count |
| `MIN_SUCCESSFUL_PROFILES` | min(2, profile count) |
| `SOL_MODEL` | `gpt-5.6-sol` |
| `SOL_REASONING_EFFORT` | `medium` |
| `OPENAI_API_URL` | `https://api.openai.com/v1` |
| `LUNIT_FM_MODEL` | `Lunit/L2-preview` |
| `LUNIT_FM_API_URL` | `https://model.hackathon.lunit.io` |
| `PATIENT_SIMULATOR_URL` | `https://patient.hackathon.lunit.io` |
| `PATIENT_SIMULATOR_MODEL` | `patient-simulator-ko` |
| `L2_TIMEOUT_SECONDS` | `180` |
| `SOL_TIMEOUT_SECONDS` | `180` |
| `PIPELINE_TIMEOUT_SECONDS` | `240` |

Secrets resolve from `OPENAI_API_KEY` and `LUNIT_FM_API_KEY` first, then their bundled
`submission_openai_key` and `submission_api_key` files. They are not logged or returned in API
errors. Environment variables are the preferred local override.

## Local health database tool

Set `L2_BACKEND=l2_plus` to replace the internal bare-L2 client used by chat
strategies with the local-first L2-plus client:

```bash
MODEL_STRATEGY=multi_patient_sol L2_BACKEND=l2_plus uvicorn app.main:app
```

L2-plus folds the conversation and plans the response as before. When the plan
needs grounding, its driver queries `resources/lunit_health.db` before making
any remote MCP tool call. Matching catalog `node_id` values route directly to
MCP node/page retrieval. If targeted retrieval returns citable evidence, the
broader L2 MCP tool loop is skipped; otherwise it remains available as a
fallback. The final user-facing draft is always generated by L2.

The bundled artifact is a knowledge-only catalog exported from
`lunit-health-db`; it has no HealthBench examples, rubrics, ideal answers, or
model outputs. Set `LUNIT_HEALTH_DB_PATH` to point at another compatible SQLite
database. `L2_PLUS_LOCAL_LIMIT` controls the local result limit (default 5).
The model-facing adapter always hard-filters searches to `kind="knowledge"`.

`baseline_l2` deliberately ignores `L2_BACKEND` and remains the canonical bare
L2 baseline. `siusiubeom_h4` enables local-first retrieval when the backend is
`l2_plus`, allowing a direct comparison without defining L2-plus as a public
chat model.
